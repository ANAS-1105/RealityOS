# RealityOS — architecture notes

## Why this shape

The product's differentiator is a *loop*, and loops are only trustworthy if the numbers that come out
of them are reproducible and the state that feeds them is owned by the right person. The architecture
is therefore split along three lines:

1. **Deterministic core** — everything numeric, pure, dependency-free, shared by server and browser.
2. **AI layer** — language only (strategies, assumptions, challenges, explanations), never numbers.
3. **Platform layer** — HTTP, auth, persistence, rate limiting: boring and explicit.

```

  schemas.ts                    zod: request bodies, LLM contracts, persisted documents
  demo.ts                       demo scenario + labels

    ml.ts                       logistic/ridge inference + MODEL_CARD metadata
    simulate.ts                 projections, feasibility, scoring, recommendation, What-If
    local-engine.ts             deterministic extraction / planning / critique / reflection
    reflect.ts                  prediction bookkeeping and outcome comparison
    internals.ts                type-only re-exports (keeps Node's type-stripping loader happy)

  services/simulations.ts       orchestration + persistence for the simulation lifecycle
```

## Request lifecycle

1. `index.ts` wraps everything in `createFreebuffAuth(...).wrap(...)`, so `/auth/freebuff/*`
   (sign-in, callback, session, sign-out) is handled before the app — and sessions are refreshed with
   the cookies the SDK returns.
2. `app.ts` assigns a request id, rejects cross-site state-changing calls with 403 using
   `isSameOriginRequest`, resolves the visitor, then routes.
3. `routes/api.ts` enforces authentication for everything except `/api/health`, initializes the
   database schema if needed, and materialises the user row.
4. Service functions do the work. Every mutation additionally re-checks ownership **before** parsing
   the body, so an id that is not yours returns 404 regardless of payload validity.
5. Responses are `Cache-Control: private, no-store`.

## The simulation pipeline

`POST /api/simulations/:id/analyze` and `…/run` stream server-sent events. Each stage event is emitted
when its agent actually returns, so the UI's progress list is real progress:

| Stage | Agent | Output |
| --- | --- | --- |
| Understanding the situation | Situation | goal, deadline, hours, active days, constraints, resources, deliverables, risks, open questions, extraction confidence |
| Extracting constraints / Mapping dependencies | — | derived counts, surfaced as progress detail |
| Generating decision paths | Planning | 3–4 strategies with per-deliverable allocations, assumptions, trade-offs, an AI success estimate |
| Simulating outcomes | Simulation (engine) | required hours, scheduled hours, expected finish date, buffer, ML completion probability, deadline risk, pressure index, flexibility, capacity utilisation, per-deliverable coverage, per-feature contributions |
| Identifying risks | Risk | option-specific failure modes with severity and mechanism |
| Challenging assumptions | Critic | falsifiable challenges, including explicit disagreement with the model's own numbers |
| Preparing the recommendation | Recommendation | ranking (computed by the engine) + reasons + why the runner-up lost |

Numbers are produced only by `src/shared/engine`. The LLM's own probability is shown separately as
"AI estimate", so the two are never conflated.

## The learning system

* Each run stores a prediction (success probability, deadline risk, pressure, expected hours,
  expected completion date, deadline) plus the exact feature vectors used.
* Recording an outcome stores the outcome, computes the gap, writes a reflection (LLM or local), and
  appends a `training_rows` entry.
* A user's **follow-through reliability** is a shrunk estimate
  `(Σ actual + prior·5) / (n + 5)` starting from the 0.72 population prior — it becomes a feature of
  the next simulation.
* A **bias correction** `mean(actual − predicted)` is applied with shrinkage `n/(n+5)` to the headline
  probabilities, so one surprising outcome cannot swing the model.
* `GET /api/profile/training-export` returns the rows in the trainer's input format;
  `npm run train -- --real <file>` refits the weights on them.

## Security posture

* Authorization is server-side on every user-scoped query (`owner = user.sub`); client-supplied ids
  decide nothing.
* State-changing requests must be same-origin, checked before authentication runs.
* Fixed-window rate limits per user per endpoint (analyze/run 12/min, What-If 120/min, …).
* Uploaded documents are parsed **in the browser**; only extracted text is sent, and images are never
  read for text. No file storage binding is needed, which removes that attack surface entirely.
* LLM keys live in server-side secrets. The browser never receives them.
* Account deletion removes profile, simulations, situations, runs, predictions, outcomes,
  comparisons, training rows and agent events for that user.

## Testing strategy

* **Unit / property level** (`tests/engine.test.mjs`): determinism, monotonicity (more hours ⇒ higher
  completion probability, lower deadline risk, higher pressure), scoring weights summing to 1,
  What-If delta direction, prediction-vs-reality arithmetic.
* **AI layer** (`tests/agents.test.mjs`): a mock provider exercises valid output, hallucinated
  deliverables, schema violations and total failure — asserting that invalid model output never
  reaches the domain model and that the reported engine mode matches what actually ran.
* **End-to-end** (`tests/api.test.mjs`): the real Worker bundle in real workerd with a real local D1
  database, driven over HTTP: 401s, foreign-origin 403s, two-account isolation, validation errors,
  the complete simulation loop, calibration, training export and account deletion.
